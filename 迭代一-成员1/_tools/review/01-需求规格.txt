### [Heading 1] 1. 项目概述

### [Heading 2] 1.1 背景与问题
高校校园内存在大量闲置教材、数码配件、文体用品与生活物资。每学期结束与开学初，教材、考研资料、耳机与数据线、球拍、小家电等物品在两个学期之间完成集中更替，大量仍具备使用价值的物品被长期闲置或直接丢弃。学生对闲置物品的处置意愿明确，但传递渠道仍以熟人关系、班级群和宿舍楼下公告栏为主，缺少轻量化、结构化的本地管理系统。
现有流转渠道存在四个结构性缺陷：
信息零散、检索困难：微信群消息在数小时内即被新消息覆盖，公告栏受物理位置限制；用户无法按分类、关键词、价格区间、成色做组合筛选，供需匹配依赖偶然刷到。
信任缺失、责任不可追溯：陌生人之间流转没有实名约束、没有信用记录、没有互评，出现爽约、物品描述不符或纠纷时无法定位责任。
过程不可追踪：口头约定不落库，「谁先申请、出让方是否同意、是否已经完成」无据可查，同一物品可能同时被承诺给多个受让方，形成重复承诺。
价值不可量化：闲置物流转带来的资源节约与减碳贡献没有任何统计口径，无法形成可展示的校园低碳数据。
通用商业二手平台面向全市场 C2C 交易，存在校园场景适配差（同校地理闭环弱）、审核与隐私不可控、账号与学生身份无绑定等问题。同时，本课程明确禁止使用 Spring 等重量级框架与 ORM 框架，并要求交付可双击运行的桌面应用，系统不得依赖服务端与网络环境。因此本系统定位为：面向单一校园的轻量本地桌面系统，以 SQLite 单文件数据库持久化全部业务数据，以分层架构与接口隔离保证可维护性与可扩展性。
本文件是迭代一（第 1–2 周）的 D1 交付物，作为后续 UML 建模、数据库设计、接口定义、编码与测试的唯一需求基线。文中所有需求编号（FR/NFR/BR/UC）、数据表名、字段名、业务规则原文均与《迭代一·共享契约-实体与接口基线》保持一致，不得另起编号体系。

### [Heading 2] 1.2 建设目标
依据题目书「完整业务闭环、可部署桌面应用、覆盖大纲核心知识点」的总体要求，本系统设定以下 5 项可度量目标，作为迭代四验收与课程评分的自检依据：
G1 业务闭环可演示：系统覆盖「注册登录 → 发布物品 → 分类/关键词检索 → 意向沟通 → 流转申请/同意/确认 → 双方评价与信用分 → 流转统计与 CSV 导出 → 管理后台」全链路，交付双击即可运行的 Jar 包，首次启动自动建库，10 分钟内可完成一次完整的流转演示。
G2 需求可判定：功能需求 17 条、非功能需求 10 条、业务规则 12 条、用例 8 个，每条需求至少给出 2 条「给定…当…则…」形式的可判定验收标准；迭代一需求评审通过率100%，除标注【建议补充】的扩展项外无遗留待确认项。
G3 数据与性能达标：物品数据量达到 5000 条时，分类 + 关键词 + 价格区间组合检索的响应时间小于 500ms；冷启动至主界面可操作小于 3s；年度区间统计小于 2s。
G4 质量可度量：Service 层核心业务规则由 JUnit 5 用例覆盖，目标行覆盖率不低于 60%，业务规则（BR-01…BR-12）正例与反例分支覆盖率 100%；交付源码无 TODO/FIXME 遗留；静态分析阻断级问题为 0。
G5 低碳价值可量化：统计模块按分类输出流转数量、成交金额与碳减排估算（kgCO₂e），估算口径与 system_config 中的碳系数键严格一致，同一数据集重复计算结果完全一致，并支持导出 UTF-8 BOM 编码的 CSV 报表。
说明：G3 中的响应时间与 G4 中的覆盖率目标为本组自定的质量门禁，题目书未给出具体数值，标【建议补充】；目标值在迭代二、迭代三通过实测记录复核，未达标时按第 9 章变更流程调整并留痕。

### [Heading 2] 1.3 系统范围与明确不做的事

### [Heading 3] 1.3.1 系统定位与纳入范围
系统为单机桌面应用，运行于 Windows 10 及以上 x64 环境，用户数据保存在程序运行目录下的单文件数据库 greencampus.db 中，初始化由 db/schema.sql 与 db/seed-data.sql 完成。纳入本期范围的能力如下：
单机桌面运行与打包交付：可双击运行的 Jar（Maven 坐标 edu.campus:green-campus:1.0.0），首次启动自动建库并加载预置数据。
账号与权限：注册、登录（含失败锁定）、密码加盐摘要存储与修改、三类角色（STUDENT / TEACHER / ADMIN）的菜单与接口双层鉴权。
物品全生命周期：发布（含图片）、修改、下架、审核（PENDING → ON_SALE / REJECTED）、分类与关键词检索、价格区间与成色筛选、收藏。
供需闭环：意向沟通消息、流转申请与状态跟踪、成交确认（跨表事务）、双方互评与信用分变更、信用分对发布权限的约束。
统计与交付能力：分类统计、碳减排估算、CSV 报表导出、关键操作日志、管理员用户管理与分类维护。
工程能力：分层架构与接口隔离、UML 类图与时序图、JUnit 5 单元测试、代码重构、至少 3 种设计模式落地、静态分析与日志。

### [Heading 2] 3.4 需求依赖与实现约束
17 条需求之间存在明确的依赖与约束关系，编码与测试须按下述顺序推进，避免出现「后置需求先行、前置能力缺失」的返工：
（1）FR-01、FR-02、FR-03、FR-04 是其余全部需求的前置能力（账号、会话、权限），必须在迭代二第 3 天前完成并通过 JUnit 用例。
（2）FR-05 → FR-06 → FR-07/08 → FR-11 → FR-12 构成「发布 → 检索 → 流转 → 完成」核心链路，其中 FR-11 的状态机与 FR-12 的跨表事务是数据一致性风险最高的两处，须优先写集成测试。
（3）FR-13 由 FR-12 的完成与评价动作触发，不得由界面直接调用 updateCredit 绕过业务校验；FR-14 与 FR-15 只统计 DONE 状态数据，依赖 FR-12 完成后的状态落库。
（4）FR-16 与 FR-17 为管理侧能力，依赖 FR-04 的权限矩阵与 BR-10 的连带处理规则；其下架、冻结动作会反向影响 FR-11 的进行中流转，测试须覆盖交叉场景。
（5）FR-10 为 FR-11 的沟通补充，不可替代流转状态记录：聊天内容不改变流转状态，流转状态只能通过 FR-11 的申请/同意/取消与 FR-12 的确认迁移。

### [Heading 2] 6.3 权限校验的实施要求
（1）双层校验：Controller 负责「按角色与状态生成可点击控件集合」，Service 负责「对每次调用校验调用者身份与目标资源归属」，两层不得重复实现同一判断逻辑，也不得互相替代。
（2）默认拒绝：新增功能或新增角色时，若权限矩阵未明确允许，一律按禁止处理，须显式登记后再开放。
（3）失败无副作用：越权请求被拒绝时不得产生任何业务数据变更，也不得泄露目标资源的敏感字段。
（4）可审计：管理类操作（FR-16、FR-17）无论成功或失败，均写 operation_log，记录操作人、操作类型、目标与结果。
