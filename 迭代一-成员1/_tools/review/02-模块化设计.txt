### [Heading 2] 1.2  设计目标
本系统的设计目标不是“把九个功能做成九个界面”，而是构造一个可在 8 周内由 3 人并行推进、在迭代四可打包交付、在答辩时可被追问设计决策的模块化桌面系统。具体目标如下：
（1）可替换：所有跨层调用都通过接口完成，替换 DAO 实现（JDBC 换缓存桩）或 Service 实现时不修改调用方代码。
（2）可测试：Service 只依赖 DAO 接口与实体，JUnit 5 可用桩实现替代真实 SQLite，单元测试无需启动数据库。
（3）事务边界集中：事务边界唯一地落在 service.impl 层（BR-07），UI 与 DAO 均不出现 commit/rollback。
（4）防御性：参数校验分两层：controller 做格式校验（BR-01/BR-12），service 做业务规则校验（BR-03～BR-10），非法输入以统一异常体系上抛。
（5）可交付：面向 Java 17 标准库与 JDBC，不引入 Spring、Hibernate 等重量级框架，保证可编译、可运行、可讲解。
（6）可扩展：新增一种排序策略或一种减排系数算法时，只新增类而不修改 ItemService；新增一类操作日志监听器时不修改流转业务。

### [Heading 2] 1.4  为什么分层，而不是简单 CRUD
题目书明确禁止“仅做简单 CRUD”。对本系统而言，简单 CRUD 的典型形态是：Swing 窗体按钮的监听器里直接书写 SQL、用 DriverManager 取连接、在 try-catch 中弹 JOptionPane。这种写法在只有一张表、一个用户角色时可以跑通，但本系统存在四个不可回避的复杂度来源：
（1）跨表事务：流转成交需要同时修改 item、trade_flow、credit_log（双方各一条）与 operation_log 四类表，任一失败必须整体回滚（BR-07）。
（2）角色权限：普通用户与管理员对同一操作（下架物品、冻结用户）的权限判定不同（BR-10），必须在业务层统一判定，不能依赖界面隐藏按钮。
（3）审计与日志：注册/登录/发布/审核/流转均须写 operation_log（BR-11），若在每个界面各自写日志，必然遗漏且不可维护。
（4）并行开发：成员2、成员3 在同一时段分别开发业务逻辑与界面，若没有稳定的接口边界，两人将互相阻塞在“类还没写完”上。
因此本系统采用分层架构：把“变化的维度”隔离到不同层。表 1-2 从工程维度对比两种构造方式的代价。
表 1-2  简单 CRUD 与本系统分层架构对照
结论：分层带来的“多写接口、多写适配代码”的成本是显性的、一次性的；而简单 CRUD 在事务一致性、并行开发与后期重构上的成本是隐性的、持续累积的。对于本系统 11 张表、9 类功能、3 人并行的规模，分层的收益显著大于成本，因此本设计选择分层，并以下述硬性依赖规则保证分层不被逐渐绕过。

### [Heading 2] 2.4  一次“发布闲置物品”请求的分层流转
为使分层不停留在图上，下面用发布物品这一用例说明一次真实请求如何贯穿各层（实现见 D4 时序图场景 2）：
（1）表现层：用户在 PublishItemFrame 填写标题、分类、价格、成色并选择图片，点击“发布”；界面只读取控件值，不判断业务规则。
（2）控制层：PublishItemFrame 把控件值封装为 Item 实体与 List<String> 图片路径，调用 ItemController.publish(item, imagePaths)；controller 用 Validator 做格式校验（标题 2–50 字、价格 ≥0、图片 ≤5 张且 jpg/png、单张 ≤2MB）。
（3）控制层到业务层：ItemController 调用 ItemService.publish(item, imagePaths)（接口，非实现类）；捕获 AppException 后按 code 映射为界面提示文案。
（4）业务层：ItemServiceImpl 校验 BR-04（信用分 < 60 拒绝发布）与 BR-05（物品状态合法性），开启事务，调用 ItemDao.insert 回填 itemId，再调用 ItemImageDao.batchInsert 写入图片记录，提交事务，最后写 operation_log（PUBLISH_ITEM）。
（5）数据访问层：ItemDaoImpl 用 PreparedStatement 执行 INSERT 并回填自增主键；ItemImageDaoImpl 批量插入图片相对路径 data/images/{itemId}/{uuid}.jpg。两者均只做 SQL，不做业务判断。
（6）异常回流：任一步骤抛 DataAccessException 时，业务层回滚并包装为 TransactionException；界面只捕获 AppException 并按 code 提示，未捕获异常写日志与 operation_log。
该用例完整映射了第 5 章的 ItemService.publish 签名、第 6 章的异常传播路径以及第 7 章工厂模式（DAO 实例获取）与观察者模式（操作日志）的落点。

### [Heading 2] 2.5  横切包的组织方式
dto、util、exception、config 不作为“层”参与调用链，而是被各层共同依赖的横切资产，其组织约定如下：
dto：仅承载数据：ItemQuery 组合检索条件、PageResult<T> 统一分页、StatisticsDTO 作统计行、UserCreditDTO / TradeDetailDTO / LoginResult 作聚合视图；不含行为逻辑。
util：仅提供无状态静态方法或单例：DbUtil（连接与事务）、PasswordUtil（PBKDF2）、Validator（正则与区间校验）、CsvExporter（导出）、ConfigManager（配置单例）、DaoFactory / ServiceFactory（工厂）。
exception：AppException 为根，9 个子类按“校验/重复/未找到/认证/锁定/权限/业务规则/数据访问/事务”分工；UI 只捕获根类型。
config：DbConfig 保存 JDBC URL 与连接参数，AppConfig 保存应用级常量（分页默认值、图片目录等）；两者只读，配置项取值优先从 system_config 表读取并由 ConfigManager 缓存。

### [Heading 2] 3.3  包内文件组织约定
为避免“一个文件塞多个公开类”导致的审查困难，包内文件遵循以下约定：
每个 .java 文件只含一个 public 顶层类型，文件名与类名一致；枚举各自独立成文件，不嵌套在实体内部。
禁止使用通配符 import（import edu.campus.recycle.*），便于 R1～R8 规则用静态检查工具定位依赖。
DAO 实现统一继承 AbstractJdbcDao（模板方法），复用连接获取、资源释放、异常转换与事务内的 executeInTransaction。
util 包内的 RowMapper<T>、ConnectionCallback<T>、TransactionCallback<T> 均为 @FunctionalInterface 回调接口：RowMapper 负责 ResultSet→实体映射，ConnectionCallback / TransactionCallback 是 AbstractJdbcDao 模板方法与 DbUtil 事务方法的可变部分，签名见 5.7 节。
DaoFactory 与 ServiceFactory 的包归属说明：契约第 8 节将其列为设计模式落点，类名已固定；本设计将两者放入 util 包（与 DbUtil、ConfigManager 同属基础设施），若迭代二评审后统一移到 config 或新建 factory 包，须由 Lead 修订契约后同步 D2/D3，禁止各自为政。
测试代码位于 src/test/java 下同名包，命名 XxxTest；测试类不属于 11 个业务包，不计入包结构约束。

本章是成员2、成员3 并行开发的“签名合同”。约定：接口共 22 个（BaseDao 1 个 + DAO 11 个 + util 回调 3 个 + Service 7 个），方法共 89 个（BaseDao 5 + DAO 53 + util 回调 3 + Service 28）。以下所有代码块均为接口声明的完整签名，为节省篇幅省略 import 语句；实际源文件中需导入 java.util.List、java.util.Optional、java.time.LocalDateTime、java.math.BigDecimal、java.nio.file.Path、java.io.IOException 以及 edu.campus.recycle 下的 entity / dto / exception 类型。方法名、参数类型与顺序、返回类型、throws 子句均逐字取自《_共享契约-实体与接口基线.md》第 5、6 节，不得改动。

### [Heading 2] 5.1  接口设计约定
（1）Optional 优先：查询单个对象一律返回 Optional<T>，禁止用 null 表示“不存在”；批量查询返回空 List 而非 null。
（2）分页约定：分页查询的 pageNo 从 1 开始、pageSize 默认 10、上限 100；越界参数由 controller 先行纠正，Service 不再重复校验。
（3）类型约定：金额 BigDecimal、时间 LocalDateTime、布尔字段 isXxx、枚举使用 enum；DAO 负责 REAL/TEXT 与 Java 类型互转。
（4）异常约定：受检异常一个也不用：所有异常继承 AppException（RuntimeException），接口上的 throws 仅用于向调用方声明业务语义，编译器不强制捕获，但代码走查要求 controller 必须处理。
（5）抽象约定：接口只声明“做什么”，不出现 SQL、Swing、Connection、ResultSet；实现细节全部留在 impl 包。

### [Heading 2] 5.7  util 回调接口（RowMapper / ConnectionCallback / TransactionCallback）

### [Heading 1] 6  异常体系

### [Heading 2] 6.1  设计目标
异常体系承担三项职责：其一，把“业务失败”与“程序缺陷”区分开——前者用 AppException 子类表达并可被界面友好提示，后者交由日志与未捕获异常处理器暴露；其二，用稳定的 code 把异常与提示文案解耦，界面不硬编码中文文案；其三，保证任何异常都不会导致数据库连接泄漏或事务悬挂。
全部继承 RuntimeException：Service 接口签名上的 throws 只作语义声明，避免方法链上层层声明受检异常。
携带 code 与 userMessage：code 供日志检索与断言（如 AUTH-001），userMessage 供界面直接展示。
保留 cause：包装底层 SQLException/IOException 时不丢失原始堆栈。
统一工厂方法：AppException.of(code, userMessage, cause)，禁止直接 new 子类时漏设 code。

### [Heading 2] 6.5  异常编号规范
code 采用“前缀-三位数字”格式，前缀表示异常类别，数字段按模块分段：001–099 用户与通用、101–199 物品与检索、201–299 流转、301–399 评价、051–099 管理员（与 001–099 段内再细分）、901–999 系统级。新增 code 必须满足：唯一、含义稳定、在表 6-2 或 ErrorMessageMapper 中登记。示例：AUTH-001 登录失败、LOCK-001 账号锁定、BR-04 信用分不足、TX-001 成交事务回滚、DB-171 流转唯一索引冲突。

### [Heading 1] 7  设计模式落点
课程要求恰当使用至少 3 种设计模式；本设计在契约第 8 节确认了 5 处必选落点与 1 个备选。本节对每个模式按“问题—方案—代码骨架—涉及类—可扩展点”五段式说明，确保每个模式都能回答“用在哪、解决什么问题、不加会怎样”三个答辩问题。模式汇总见表 7-1。

### [Heading 2] 7.1  单例（Singleton）
问题：SQLite 桌面应用若每次操作都 DriverManager.getConnection，会反复打开数据库文件；system_config 表若每个界面各自读取，会重复解析且配置不一致；Maven 单进程桌面程序中这些资源天然全局唯一。
方案：DbUtil 与 ConfigManager 使用“静态内部类持有实例”的懒加载单例（线程安全且无同步开销）；构造函数私有化，唯一入口为 getInstance()；DbUtil 内部维护连接模板与事务方法，ConfigManager 首次访问时加载 system_config 并缓存。
代码 7-1  单例骨架（DbUtil；ConfigManager 同构）
public final class DbUtil {
    private DbUtil() { }
    private static class Holder { private static final DbUtil INSTANCE = new DbUtil(); }
    public static DbUtil getInstance() { return Holder.INSTANCE; }
    public Connection getConnection() throws DataAccessException { /* DriverManager + DbConfig */ }
    public void beginTransaction(Connection c) { /* setAutoCommit(false) */ }
    public void commit(Connection c) { /* commit + 归还 */ }
    public void rollback(Connection c) { /* rollback + 归还 */ }
}
涉及类：DbUtil、ConfigManager（util/config 包）、AbstractJdbcDao（调用 DbUtil 取连接）。可扩展点：若后续引入连接池（如 HikariCP，需评估课程“禁止重量级框架”约束），只改 DbUtil 内部实现，调用方与 DAO 均无感知；配置热更新只需在 ConfigManager 增加 reload()。

### [Heading 2] 7.2  工厂（Factory）
问题：上层若直接 new UserDaoImpl()、new TradeServiceImpl()，则在单元测试中无法替换为桩实现，且 DAO 实现类名变化会波及所有调用方——这正是依赖倒置原则要解决的问题。
方案：DaoFactory 与 ServiceFactory 按需返回接口实例：DAO 由枚举/Class 描述符决定（便于替换为内存实现），Service 由无参工厂方法返回单例实现（ServiceImpl 内部通过 DaoFactory 获取 DAO）；调用方只声明接口类型。
代码 7-2  工厂骨架（DaoFactory / ServiceFactory）
public final class DaoFactory {
    private DaoFactory() { }
    public static UserDao userDao()   { return new UserDaoImpl(DbUtil.getInstance()); }
    public static ItemDao itemDao()   { return new ItemDaoImpl(DbUtil.getInstance()); }
    public static TradeFlowDao tradeFlowDao() { return new TradeFlowDaoImpl(DbUtil.getInstance()); }
    /* … 11 个 DAO 各一个静态工厂方法 */
}
// 测试中可注入桩：DaoFactory.setUserDao(new FakeUserDao());
public final class ServiceFactory {
    private ServiceFactory() { }
    public static UserService userService() { return UserServiceImpl.INSTANCE; }
}
涉及类：DaoFactory、ServiceFactory、11 个 DaoImpl、7 个 ServiceImpl。可扩展点：新增 DAO 只需在工厂加一行并实现接口；替换某个 DAO 为“带缓存的实现”不影响 Service；测试通过 setXxx 注入桩对象实现零数据库单元测试。

### [Heading 2] 7.3  策略（Strategy）
问题：物品检索支持“最新发布/价格升序/价格降序/信用优先”四种排序，若在 ItemServiceImpl 内写 if-else 拼 ORDER BY，新增排序方式就要修改 Service 并重跑全部测试；低碳减排系数按分类不同，硬编码在计算公式中同样难以扩展。
方案：定义 ItemSortStrategy 接口封装“排序片段生成”算法，ItemServiceImpl.search 根据 ItemQuery.sortBy 从策略表选择；定义 CarbonFactorStrategy 接口封装“分类→减排系数”映射，StatisticServiceImpl 只调用接口，系数值来自 system_config。
代码 7-3  策略骨架（ItemSortStrategy；CarbonFactorStrategy 同构）
public interface ItemSortStrategy {
    String name();                       // LATEST / PRICE_ASC / PRICE_DESC / CREDIT_FIRST
    String buildOrderBy(ItemQuery q);    // 返回安全的 ORDER BY 片段，禁止拼接用户输入
}
public class PriceAscSortStrategy implements ItemSortStrategy {
    public String name() { return "PRICE_ASC"; }
    public String buildOrderBy(ItemQuery q) { return " ORDER BY i.price ASC, i.id DESC"; }
}
// ItemServiceImpl.search：ItemSortStrategy s = sortStrategies.getOrDefault(q.getSortBy(), latest);
涉及类：ItemSortStrategy 及 4 个实现、CarbonFactorStrategy 及实现、ItemServiceImpl、StatisticServiceImpl。可扩展点：新增“距离优先/成色优先”只需新增实现类并注册；策略实现可独立做单元测试（断言返回的 ORDER BY 片段），不必构造数据库。

### [Heading 2] 7.4  观察者（Observer）
问题：流转成交完成后需要做四件事：改物品状态、给双方加信用分并写流水、写操作日志、更新统计缓存。若全部写在 TradeServiceImpl.confirm 中，方法会膨胀且每加一个副作用都要改成交逻辑，违反开闭原则。
方案：定义 ItemEventBus（发布/订阅）与监听器统一接口；TradeServiceImpl 在事务提交成功后发布 ItemEvent，CreditChangeListener、OperationLogListener、StatisticListener 各自订阅处理。事件携带 itemId、flowId、operatorId，不携带 Connection——需要事务一致性的写操作仍留在交易方法内部，事件只承担“事务后可容忍重试”的副作用。
代码 7-4  观察者骨架（ItemEventBus + 监听器）
public interface ItemEventListener { void onEvent(ItemEvent e); }
public class SimpleItemEventBus {
    private final Map<ItemEventType, List<ItemEventListener>> listeners = new EnumMap<>(ItemEventType.class);
    public void subscribe(ItemEventType t, ItemEventListener l) { listeners.computeIfAbsent(t, k -> new ArrayList<>()).add(l); }
    public void publish(ItemEvent e) { listeners.getOrDefault(e.getType(), List.of()).forEach(l -> l.onEvent(e)); }
}
// TradeServiceImpl.confirm 末尾：eventBus.publish(new ItemEvent(FLOW_DONE, itemId, flowId, operatorId));
涉及类：ItemEventBus、ItemEvent、ItemEventListener、CreditChangeListener、OperationLogListener、StatisticListener、TradeServiceImpl、ReviewServiceImpl。可扩展点：新增“邮件通知/桌面提醒”只需新增监听器并订阅，成交方法不改；测试可注册计数监听器断言事件被发布一次。

### [Heading 2] 7.5  模板方法（Template Method）
问题：JDBC 代码天然重复——拿连接、创建 PreparedStatement、绑定参数、执行、处理 ResultSet、在 finally 中关闭资源、把 SQLException 转成 DataAccessException。11 个 DAO 若各写一遍，既是代码坏味道（重复代码），也容易漏关资源导致连接泄漏。
方案：抽象类 AbstractJdbcDao 定义查询/更新的执行骨架（final 方法），把“SQL 文本、参数绑定、行映射”留给子类实现（抽象方法）；AbstractCsvExporter 以 final export 固定“写表头—写数据行—落盘—异常转换”流程，子类只提供数据行。两个模板方法分别消除数据访问层与导出层的重复。
代码 7-5  模板方法骨架（AbstractJdbcDao；AbstractCsvExporter 同构）
public abstract class AbstractJdbcDao<T, ID> implements BaseDao<T, ID> {
    protected final <R> R query(String sql, StatementBinder binder, RowMapper<R> mapper) {
        try (Connection c = DbUtil.getInstance().getConnection();
             PreparedStatement ps = c.prepareStatement(sql)) {
            binder.bind(ps);
            try (ResultSet rs = ps.executeQuery()) { return mapper.map(rs); }
        } catch (SQLException e) {
            throw AppException.of("DB-101", "数据查询失败", e);   // 模板统一转换异常
        }
    }
}
// 子类只写：sqlFindById() + bind + mapRow，不再出现 try-with-resources
涉及类：AbstractJdbcDao（11 个 DAO 实现继承）、AbstractCsvExporter（StatisticCsvExporter 继承）、DbUtil。可扩展点：新增 DAO 自动获得资源释放与异常转换；若要统一加 SQL 耗时日志，只改模板方法一处；模板方法使 DAO 实现类只剩 3 个短方法，便于代码走查。

### [Heading 2] 7.6  建造者（Builder）——备选模式【建议补充】
问题：物品检索条件有 keyword、categoryId、minPrice、maxPrice、tradeType、status、ownerId、sortBy、pageNo、pageSize 共 10 个，其中 8 个可选。若用构造器传参，将出现“10 个参数、一半是 null”的超长参数表，调用处极易把参数位置写错。
方案：ItemQueryBuilder 提供链式设置方法，每个方法返回 this，build() 时统一处理默认值（pageNo=1、pageSize=10）与合法性预检（minPrice ≤ maxPrice）；ItemQuery 本身保持不可变或包内可写。该模式是备选，若迭代二时间紧张可不实现，但检索界面涉及 8 个可选条件，建议实现以降低出错概率。

public class ItemQueryBuilder {
    private final ItemQuery q = new ItemQuery();
    public ItemQueryBuilder keyword(String k) { q.setKeyword(k); return this; }
    public ItemQueryBuilder categoryId(Integer id) { q.setCategoryId(id); return this; }
    public ItemQueryBuilder priceRange(BigDecimal min, BigDecimal max) { q.setMinPrice(min); q.setMaxPrice(max); return this; }
    public ItemQueryBuilder page(int pageNo, int pageSize) { q.setPageNo(pageNo); q.setPageSize(pageSize); return this; }
    public ItemQuery build() { /* 默认值 + min<=max 预检，非法抛 ValidationException */ return q; }
}

### [Heading 2] 9.3  事件驱动约定
Swing 是单线程模型，界面卡死与线程安全问题大多来自“在 EDT 中做数据库查询”。本节给出强制约定，成员3 的所有事件监听器必须遵守，代码走查时逐条核对。
（1）后台执行：所有 Service 调用放到 SwingWorker.doInBackground()；done() 中再更新控件与表格模型。
（2）EDT 规则：禁止在 doInBackground() 中操作任何 Swing 组件；禁止在 EDT 中 DriverManager、文件 IO、sleep。
（3）防重复提交：按钮点击后立即 setEnabled(false)，done()/异常分支 finally 中恢复，防止重复提交（成交、评价等幂等敏感操作必须做）。
（4）统一异常：catch 统一捕获 AppException，经 ErrorMessageMapper 按 code 映射文案；捕获到其他异常说明分层被绕过，须修正。
（5）表格模型：TableModel 继承 AbstractTableModel，提供 setRows(List<T>) 与 getRow(int) 方法；禁止用 DefaultTableModel 直接塞 Object[]（丢失类型）。
（6）空态与失败态：列表为空时显示“暂无数据”占位标签；加载中显示进度条或禁用按钮；错误后保留用户已填内容，不清空表单。
（7）二次确认与刷新：确认成交/下架/冻结前 JOptionPane 二次确认；成功操作后刷新受影响列表（成交后同时刷新物品与流转两个视图）。

控制层 | controller | 接收界面参数并做格式校验入口；调用 Service；把实体/DTO 封装为界面可直接消费的结果；把异常翻译为提示文案。 | service（接口）、dto、entity、exception、util（Validator） | 禁止写业务规则判定（如信用分阈值）；禁止直接调用 dao；禁止持有 Connection
业务层 | service / service.impl | 实现 BR-01～BR-12；编排多个 DAO 完成一次业务用例；声明事务边界；触发领域事件（观察者）。 | dao（接口）、entity、dto、util、exception、config；impl 额外依赖 impl 的 DAO 由工厂获得 | 禁止出现 Swing 类；禁止自己拼 SQL；禁止 catch 后吞掉异常不记录日志
数据访问层 | dao / dao.impl | 执行 SQL、映射 ResultSet 到实体、回填自增主键；用 PreparedStatement 防注入；以 Optional 表达不存在。 | entity、dto、util（DbUtil）、exception、config | 禁止业务规则判定；禁止开启/提交事务（事务由 service 控制）；禁止返回 null 表示查询失败
实体层 | entity | 与 11 张表一一对应的数据载体，含 5 个枚举；字段名与表字段一一对应。 | 无（仅 java.time / java.math） | 禁止引入 DAO/Service 依赖；禁止写 SQL；禁止放置业务方法
横切 | dto / util / exception / config | dto：跨层传输对象（查询条件、分页结果、统计行）；util：无状态工具；exception：统一异常；config：配置常量与读取。 | exception/util/config 可被全部层依赖；dto 被 ui/controller/service/dao 共享 | 禁止横切包反向依赖 ui/controller/service/dao（否则形成循环依赖）

编号 | 规则 | 允许 | 禁止 | 检查方式
R1 | 单向依赖 | 上层 import 下层 | 下层 import 上层 | 检查每个源文件的 import 段所属包
R2 | 禁止跨层 | ui→controller→service→dao 逐层调用 | ui 直接调 service.impl 或 dao；controller 直接调 dao | grep “DaoImpl|Dao” in ui/controller
R3 | 面向接口 | new 实现类只出现在工厂类中 | 业务代码出现 new UserDaoImpl() / new ItemServiceImpl() | grep “new .*Impl(” 排除工厂与测试
R4 | 实现类不外泄 | 接口方法的返回类型只出现接口、实体、DTO 与 JDK 类型 | Service 接口返回 dao.impl 类型 | 检查 service 包 import
R5 | 事务单一入口 | service.impl 调用 DbUtil.begin/commit/rollback | ui、controller、dao 中出现 commit/rollback | grep “commit(|rollback(”
R6 | 无 Swing 泄漏 | ui 包 import javax.swing | service/dao/entity/util 中出现 javax.swing | grep “javax.swing” 限定包范围
R7 | SQL 唯一落点 | SQL 字符串只出现在 dao.impl | controller/service 中出现 “SELECT|INSERT|UPDATE|DELETE ” | grep 关键字排除 dao.impl
R8 | 异常单向 | 业务失败抛 AppException 子类 | return null / return false 掩盖失败（除约定为布尔的查询） | 走查 catch 块与返回值
